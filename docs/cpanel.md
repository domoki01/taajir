# النشر على استضافة cPanel مشتركة

هذا الدليل لتجربة أولى: تشغيل الموقع على حساب cPanel عادي بدل Firebase App
Hosting. النشر الرسمي يبقى App Hosting (`apphosting.yaml`)، ولا شيء ممّا هنا
يغيّره — إعداد cPanel كلّه خلف متغيّر بيئة مطفأ افتراضياً.

## 1. هل تصلح استضافتك أصلاً؟

الموقع **ليس صفحات HTML ساكنة**. كل الصفحات تقريباً تُبنى عند الطلب
(`force-dynamic`)، والنشر والتعديل والإشراف تمرّ كلها عبر Server Actions
وfirebase-admin. يعني لا بد من **Node.js يعمل على الخادم**. الاستضافة التي لا
تقدّم إلا PHP لا يمكنها تشغيل هذا المشروع، لا بتصدير ساكن ولا بأي حيلة أخرى —
التصدير الساكن يُسقط تسجيل الدخول والنشر والإشراف، أي كل ما يجعل الموقع موقعاً.

تحقّق من هذه الخمسة قبل أي شيء:

| المطلوب                                              | أين تتأكّد                                         |
| ---------------------------------------------------- | -------------------------------------------------- |
| خيار **Setup Node.js App** في لوحة cPanel            | قسم Software                                       |
| **Node 20.9 أو أحدث** (Next 16 يرفض ما دونه)         | قائمة الإصدارات داخل نفس الشاشة                    |
| **اتصال صادر على المنفذ 443** نحو `*.googleapis.com` | يفحصه `preflight.js` لاحقاً                        |
| **‏200 ميغابايت** مساحة حرّة على الأقل               | File Manager أو `df`                               |
| **‏512 ميغابايت** ذاكرة للتطبيق                      | خطة الاستضافة؛ أقلّ من ذلك يُقتل التطبيق تحت الضغط |

المنفذ 443 الصادر هو الفخّ الحقيقي: كثير من الاستضافات المشتركة تمنع الاتصالات
الصادرة، والنتيجة أن الموقع يفتح ثم تتجمّد كل صفحة تلمس Firestore حتى تنتهي
مهلتها. إن لم يمرّ الفحص، اطلب من الدعم فتحه صراحةً نحو `*.googleapis.com`.

## 2. البناء على جهازك (لا على الاستضافة)

البناء يحتاج ذاكرة ووقت معالج أكثر ممّا تسمح به الاستضافة المشتركة عادةً، ولهذا
يُبنى المشروع عندك ويُرفع جاهزاً:

```bash
NEXT_PUBLIC_SITE_URL=https://test.taajirdz.com \
NEXT_IMAGE_UNOPTIMIZED=true \
npm run build:cpanel -- --slim
```

- `NEXT_PUBLIC_SITE_URL` **إلزامي وقت البناء**: الروابط القانونية (canonical)
  وخريطة الموقع ورابط الدعوة وبطاقات المشاركة كلها تُطبع داخل الصفحات وقت
  البناء. وضعه في ملف البيئة على الخادم وحده يترك كل رابط يشير إلى العنوان
  القديم. ضع هنا العنوان الذي ستفتح به الموقع فعلاً (نطاق فرعي للتجربة مثلاً).
- `NEXT_IMAGE_UNOPTIMIZED=true` موصى به في التجربة الأولى: يُسلّم الصور من
  Firebase Storage كما هي بدل تحويلها إلى AVIF/WebP على الخادم. التحويل هو أسرع
  طريق لاصطدام بحدّ المعالج في الاستضافة المشتركة، والعَرَض — عملية تُقتل في
  منتصف الطلب — لا يشبه سببه أبداً. احذفه لاحقاً إذا أردت الصور المحسّنة.
- `--slim` يحذف نسخ sharp التي لا تعمل على هذه الاستضافة (musl وWebAssembly)
  فيوفّر ~26 ميغابايت. اتركه إن كانت استضافتك على Alpine أو معالج ARM.

الناتج ملفّان: مجلّد `dist/cpanel/` وأرشيف `dist/taajir-cpanel.tgz` — حوالي 9
ميغابايت مضغوطاً بهذه الأوامر، و17 إن أبقيت تحسين الصور.

داخل الحزمة ملف `build-info.json` يسجّل العنوان الذي بُنيت له، وهل تحسّن الصور،
ومتى بُنيت. القيمتان الأوليان مطبوعتان داخل الصفحات ولا تُقرآن من الخارج بأي
طريقة أخرى — وهذا الملف هو ما يخبرك بعد ستة أسابيع أي نسخة على الخادم.

## 3. الرفع

ارفع **الأرشيف** لا المجلّد: نماذج الرفع في الاستضافة المشتركة تنقل ملفاً واحداً
في كل مرة، والحزمة فيها آلاف الملفات — الفرق بين دقائق وساعات.

1. File Manager ← اذهب إلى مجلّد المنزل (‏`/home/USER`)، **خارج `public_html`**.
2. أنشئ مجلّداً باسم `taajir` وارفع فيه `taajir-cpanel.tgz`.
3. Extract، ثم احذف الأرشيف.

**خارج `public_html` ليست تفصيلة**: ملف البيئة الذي سيحمل مفتاح حساب الخدمة يجلس
بجانب `app.js`. داخل `public_html` يصير ملفاً يمكن تنزيله من المتصفّح.

## 4. ملف البيئة

في `/home/USER/taajir` انسخ `env.example` إلى `.env.production` وعمّره. مفتاح
حساب الخدمة يُوضع مُرمَّزاً بـ base64 لأن JSON فيه أسطر جديدة وملفّ البيئة سطر
واحد لكل قيمة:

```bash
base64 -w0 service-account.json     # على لينكس/ماك
```

(في File Manager، إن لم تظهر الملفات التي تبدأ بنقطة: Settings ← Show Hidden
Files. أو سَمِّ الملف `env.production` بدون نقطة — التطبيق يقرأ الاسمين.)

ما **لا** يوضع هنا: أي متغيّر يبدأ بـ `NEXT_PUBLIC_` (ومنه `NEXT_PUBLIC_SITE_URL`)
ولا `NEXT_IMAGE_UNOPTIMIZED`. هذه يستبدلها المترجم بقيمتها أثناء البناء فلا يبقى
منها شيء يُقرأ وقت التشغيل؛ وضعها هنا يبدو كأنه نجح ولا يغيّر حرفاً. تغييرها
يعني إعادة البناء والرفع، لا تعديل هذا الملف.

الحدّ الأدنى للتشغيل متغيّر واحد: `FIREBASE_SERVICE_ACCOUNT_JSON`.
على App Hosting لا وجود للأول لأن Cloud Run يمنح التطبيق هوية جاهزة؛ خارج بنية
Google لا يوجد هذا البديل، فبدونه يفشل كل تسجيل دخول وكل نشر وكل إشراف.

## 5. الفحص قبل التشغيل

إن كان لديك SSH:

```bash
cd ~/taajir && node preflight.js
```

يطبع أولاً بطاقة الحزمة (متى بُنيت ولأي عنوان)، ثم يفحص إصدار Node، وملف البيئة، واكتمال الحزمة، وصلاحية الكتابة (يحتاجها تخزين
الصفحات المُعاد توليدها)، وsharp، والاتصال الصادر نحو Google، ثم قراءة فعلية من
Firestore بالمفتاح الذي وضعته. يخرج بالرمز 0 إذا نجح كل ما هو إلزامي.

بلا SSH: شغّل التطبيق أولاً (الخطوة التالية) ثم افتح Terminal من داخل شاشة
Setup Node.js App — فيها زرّ يفتح جلسة داخل بيئة التطبيق.

## 6. إعداد التطبيق في cPanel

Software ← **Setup Node.js App** ← Create Application:

| الحقل                    | القيمة                          |
| ------------------------ | ------------------------------- |
| Node.js version          | ‏20.9 فأعلى                     |
| Application mode         | Production                      |
| Application root         | `taajir`                        |
| Application URL          | النطاق أو النطاق الفرعي للتجربة |
| Application startup file | `app.js`                        |

ثم **Create**، ثم **Restart**.

- **لا تضغط «Run NPM Install»**. الحزمة كاملة ومبنيّة؛ الزرّ يحاول تثبيت كل شيء
  فوقها ويستهلك حصّتك. (`package.json` في الحزمة لا يذكر أي اعتماد، تحسّباً.)
- **لا تضع التطبيق في مجلّد فرعي من النطاق** (‏`example.com/taajir`). الموقع مبني
  على أنه في جذر النطاق؛ المجلّد الفرعي يحتاج `basePath` في `next.config.ts`
  وإعادة بناء.
- Passenger هو من يشغّل `app.js` ويمسك المنفذ بنفسه، فلا داعي لضبط `PORT`.

## 7. بعد التشغيل

1. **Firebase Console ← Authentication ← Settings ← Authorized domains**: أضف
   نطاق التجربة. بدونه يفشل تسجيل الدخول برسالة `auth/unauthorized-domain`، وهو
   أكثر ما يُنسى في أول نشر على نطاق جديد.
2. افتح الصفحة الرئيسية، ثم إعلاناً، ثم `/diagnostic` — هذه الأخيرة تطبع الحالة
   الخام لكل ما يمكن أن يفشل بصمت.
3. جرّب دورة كاملة: تسجيل دخول ← نشر إعلان ← ظهوره في القائمة. هذا ما يثبت أن
   Server Actions وfirebase-admin يعملان، لا مجرد فتح الصفحة الأولى.

إن ظهر الموقع بلا تنسيق (HTML خام)، فالناقص `.next/static` — يعني الحزمة رُفعت
ناقصة؛ أعد الرفع من الأرشيف.

## 8. مهمة الكرون (اختيارية)

إن أردت إطلاقاً مبرمجاً بدل اليدوي: cPanel ← Cron Jobs، مع نفس `CRON_SECRET`
الموضوع في ملف البيئة:

```
curl -fsS -H "Authorization: Bearer YOUR_CRON_SECRET" https://test.taajirdz.com/api/cron/launch
```

بدون المتغيّر يردّ المسار 503 ويبقى الإطلاق يدوياً — وهذا سلوك مقصود.

## 9. ما الذي ستخسره مقابل ذلك

هذه التجربة تعمل، لكنها ليست App Hosting:

- **عملية واحدة بلا توسّع**. Passenger يشغّل نسخة واحدة؛ لا `minInstances` ولا
  `maxInstances`، والضغط يعني بطئاً لا نسخة ثانية.
- **إيقاف عند الخمول**. Passenger ينهي التطبيق بعد فترة سكون ويعيد تشغيله عند
  أول طلب: بضع ثوانٍ انتظاراً، وذاكرة الكاش تبدأ فارغة.
- **حدود المعالج والذاكرة** مشتركة مع بقيّة الحساب. تحسين الصور أول ما يصطدم بها
  (لذلك `NEXT_IMAGE_UNOPTIMIZED=true` في التجربة الأولى).
- **لا أسرار مُدارة**. مفتاح حساب الخدمة ملفّ على القرص، لا قيمة في Secret
  Manager. احذفه من الحساب متى انتهت التجربة، ودوّر المفتاح إن شككت في تسرّبه.
- **الصفحات المُعاد توليدها تُخزَّن على القرص** داخل `.next/cache` وتحتسب من حصّة
  مساحتك، وتُمحى مع كل نشر جديد.
- **لا نشر تلقائي**. كل تحديث = بناء عندك ← رفع ← Restart.

## 10. العودة إلى App Hosting

لا شيء ينبغي التراجع عنه. `output: "standalone"` لا يُفعَّل إلا حين
`NEXT_OUTPUT=standalone`، وتعطيل تحسين الصور لا يُفعَّل إلا حين
`NEXT_IMAGE_UNOPTIMIZED=true`، وكلاهما غير موجود في `apphosting.yaml`. الدفع إلى
`main` ينشر كالعادة.
